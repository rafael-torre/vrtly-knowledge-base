# DB90 Companion System

**New here?** Read [GETTING-STARTED.md](../GETTING-STARTED.md) first (2 min). This file is the full reference.

The DB90 Companion is an ambient AI documentation guide built into your editor. It understands the three-layer documentation model, reads your project state on session start, and provides layer-aware guidance as you work.

## Quick Start

### 1. Initialize the Companion

```bash
companion/init.sh
```

This one-time setup:
- Copies companion files into `.cursor/` (Cursor's configuration folder)
- Creates `.companion.yaml` from the example (edit with your name and role)
- Registers hooks and skills with Cursor
- Adds session files to `.gitignore`

The companion is now wired into Cursor. Next time you start a session, the `session-start` hook runs automatically and generates a project state summary.

### 2. Edit `.companion.yaml`

After running `init.sh`, you'll have a `.companion.yaml` file in the repo root. Open it and fill in your details:

```yaml
name: "Your Name"
role: tech-lead  # pm | designer | tech-lead | developer | engagement-lead
```

Your role guides the companion's suggestions:
- **pm**: Focus on user problems, market fit, priorities
- **designer**: Focus on UX, accessibility, interaction flows
- **tech-lead**: Focus on architecture, technical risks, maintainability
- **developer**: Focus on implementation details, testing, debugging
- **engagement-lead**: Focus on communication, dependencies, stakeholder alignment

### 3. Start Working

Open any document in the documentation framework and start editing. The companion rule (`.cursor/rules/db90-companion.mdc`) is always active. It will:

- Detect which layer you're working in (Layer 1: Product, Layer 2: Design, Layer 3: Architecture)
- Load upstream `final/` documents from `relates_to` for context
- Suggest the appropriate skill for your current task
- Enforce layer sequencing (e.g., can't finalize a Layer 2 design before Layer 1 is consensus)

## How It Works

### Architecture

```
companion/ (repo root — source of truth, committed)
├── init.sh                 ← Run this once
├── README.md               ← This file
├── .companion.yaml.example ← Template for per-session config
├── rules/
│   └── db90-companion.mdc  ← The brain
├── hooks.json              ← Hook registration template
├── hooks/
│   ├── scan-project-state.sh
│   └── update-metadata.sh
└── skills/
    ├── scan-project-state/
    └── session-handoff/

.cursor/ (wired by init.sh, partially gitignored)
├── rules/db90-companion.mdc
├── hooks.json
├── hooks/ (scan + update scripts)
├── skills/ (companion + layer-specific)
├── session-state.md       ← Generated by sessionStart hook (gitignored)
└── session-handoff.md     ← Generated by session-handoff skill (gitignored)

.companion.yaml            ← Your personal config (gitignored)
```

### Two Hooks

**`scan-project-state.sh`** (runs on `sessionStart`)
- Scans all `layers/*/final/*.md` documents
- Reads frontmatter: `status`, `last_updated`, `relates_to`
- Generates `.cursor/session-state.md` with a summary of what needs attention
- The rule reads this and surfaces it in the chat

**`update-metadata.sh`** (runs on `afterFileEdit`, scoped to `layers/**/final/**/*.md`)
- Auto-updates `last_updated` to today's date
- Reads `relates_to` and cascades `status: needs_review` to downstream docs
- Makes the documentation cascade automatic — no manual notifications needed

### Three Session Modes

**Resume** (on session start)
- Rule reads `.cursor/session-state.md` and `.companion.yaml`
- Surfaces docs needing review, update, or in progress
- Proposes concrete focused scope for this session

**Guided** (during active work)
- Rule detects your current document's layer (0-4)
- Loads upstream Layer N-1 finals automatically
- Enforces sequencing (can't skip layers; Layer 0 informs Layer 1, etc.)
- Suggests the right skill for drafting, reviewing, or refining

**Handoff** (ending or drifting session)
- Run the `session-handoff` skill
- Captures decisions, blockers, and next steps
- Outputs `.cursor/session-handoff.md` for seamless continuity
- Next session links it in the initial query to restore context

## Skills

### Companion-Level Skills (always available)

- **`scan-project-state`** — On-demand health check. Shows what needs review, what's stale, what's in progress.
- **`session-handoff`** — Capture decisions and context when a session ends or drifts.

### Layer-Specific Skills (loaded based on current layer)

- **`draft-feature-spec`** (Layer 1) — Draft a product feature specification from raw inputs (user story, constraints).
- **`draft-design-spec`** (Layer 2) — Draft a design specification from an approved Layer 1 final.
- **`draft-technical-spec`** (Layer 3) — Draft a technical specification from Layer 1 + 2 finals.

**Note**: Skills for Layer 0 (Business) and Layer 4 (Implementation) are not yet included. These can be added based on your team's needs.

All skills are fully self-contained and documented. Invoke them when you're ready to draft a new layer or get a project snapshot.

## Configuration

### `.companion.yaml`

Created by `init.sh` from `.companion.yaml.example`. Gitignored — follows the person, not the project.

```yaml
name: "Your Name"
role: tech-lead
```

Roles customize the rule's guidance. Use one of: `pm`, `designer`, `tech-lead`, `developer`, `engagement-lead`.

### Frontmatter Conventions

All `final/` docs should have YAML frontmatter:

```yaml
---
title: "Document Title"
owner: "Name or Team"
status: draft | needs_review | in_progress | consensus | needs_update
last_updated: YYYY-MM-DD
relates_to:
  - layers/layer-1-product/final/features/feature-name.md
  - layers/layer-2-design/final/flows/design-decision.md
---
```

Key fields:
- `status`: Drives the cascade. When a `final/` doc is edited, the hook cascades `needs_review` to all docs listed in `relates_to`.
- `last_updated`: Auto-maintained by the hook (you can edit it; the hook will overwrite on next save).
- `relates_to`: Upstream docs this one depends on. The rule loads these for context.

## Typical Workflows

### Drafting a New Feature

1. **Gather inputs** — Get user story, problem statement, success criteria.
2. **Use `draft-feature-spec`** — Skill guides you through Layer 1 draft.
3. **Product review** — Team reviews in `draft/`; feedback incorporated.
4. **Move to `final/`** — Change `status: consensus` once approved.
5. **Layer 2 begins** — Design team uses `draft-design-spec`, which loads your Layer 1 final as context.

### Long or Drifting Session

1. **Mid-session or end-of-day** — Run `session-handoff`.
2. **Captures** — What was done, blockers, next steps, relevant docs.
3. **Next session** — Link the handoff in your initial query to restore context.

### Checking Project Health

1. **Anytime** — Use `scan-project-state` for a snapshot.
2. **Review output** — See what's stale, in progress, needs review.
3. **Prioritize** — Focus work on the most pressing items.

### Adding New Features

- Companion-level skills (scan, handoff) and layer-specific skills are auto-discovered after `init.sh`.
- New layer-specific skills go in `layers/layer-X/tools/[skill-name]/SKILL.md`.
- Re-run `init.sh` to copy new skills into `.cursor/skills/` for Cursor to discover.

## Adapting for Other Editors

The companion is designed for Cursor but can adapt to other editors:

- **Hooks** → Replace with your editor's hook system (e.g., pre-commit hooks, file watchers, LSP plugins)
- **Rules** → Replace `.mdc` with your editor's guidance format (e.g., VS Code AI extension config, Emacs Lisp, Vim Lua)
- **Skills** → `.md` skills are portable; they describe workflows and don't depend on Cursor

The core idea is portable: **pair an always-on rule with layer-aware hooks and self-contained skill documentation**.

## Troubleshooting

### "The companion rule isn't activating"

1. Did you run `init.sh`? Rules are copied to `.cursor/rules/`, and Cursor scans that folder on startup.
2. Restart Cursor after running `init.sh`.
3. Check that `.cursor/rules/db90-companion.mdc` exists and has `alwaysApply: true`.

### "The hooks aren't running"

1. Check that `.cursor/hooks.json` exists and is valid JSON.
2. Verify hook script paths in `hooks.json` are correct (e.g., `${CURSOR_WORKSPACE_ROOT}/companion/hooks/scan-project-state.sh`).
3. Ensure hook scripts have execute permissions (`chmod +x .cursor/hooks/*.sh`).
4. Hooks run after Cursor detects events (session start, file edit); there may be a delay.

### ".companion.yaml isn't being read"

1. Did you create `.companion.yaml` after running `init.sh`?
2. Check the format matches the example (YAML, not JSON).
3. The rule loads it once at session start; if you edit it mid-session, you may need to restart Cursor for the new role guidance.

### "session-state.md doesn't exist"

1. Start a new session (close and reopen Cursor).
2. The `sessionStart` hook should run and generate it.
3. If it's still missing, check hook permissions and event subscriptions in `.cursor/hooks.json`.

## Contributing

To improve the companion:

1. Edit source files in `companion/`
2. Re-run `companion/init.sh` to wire changes into `.cursor/`
3. Test in Cursor and gather feedback
4. Commit improvements to `companion/` (they're the source of truth)

The system is designed to evolve: companion files are versioned in the repo, so teams can sync improvements by pulling the latest `companion/` folder.
